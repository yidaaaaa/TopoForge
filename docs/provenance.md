# Provenance

Each build writes source checksums; dataset provider/name/version/type; distinct source and processed horizontal resolution/grid shape; vertical CRS/datum or `unknown`; acquisition period; license/attribution; source URLs; original NoData and interpolation percentages; projection/resampling pipeline; horizontal scale; baseline; robust elevation range; vertical exaggeration; geometry method; output format writer; validation; and slicer evidence. For the default P2S target, provenance also records the official Bambu Studio asset/version/hash, flattened machine/process/filament preset hashes, resolved print parameters, normative-check result, G-code metrics, Bambu project 3MF hash, reopen/reslice result, and the release-gate decision.

`build_manifest.json` binds artifacts to SHA-256 values. `build_config.resolved.yaml` records all defaults and CLI overrides. `original_nodata_mask.tif` preserves the pre-interpolation mask. `manufacturing_preflight.json` records the resolved printer profile/volume, model dimensions and headroom, source/processed grid cells, hard cell/triangle/memory gates and utilization, physical sample spacing, requested/resolved vertical exaggeration, height-limit action, warnings, and suggested actions. The identical preflight object is embedded in `validation.json` and `provenance.json` and is cross-checked during bundle verification. Dataset rights are not replaced by the Apache-2.0 code license.


Sampling/fidelity fields include `resource_budget_mode`, `max_estimated_triangles`, and `source_horizontal_resolution_m`, `processed_horizontal_resolution_m`, `source_grid_shape`, `processed_grid_shape`, `downsampling_factor`, `physical_sample_spacing_mm`, `estimated_triangle_count`, raw/processed elevation extrema, raw/processed peak coordinates, peak loss/shift and thresholds, `sampling_decision_reasons`, warnings, and `terrain_fidelity_status`. Published summit elevations are contextual comparisons only and always record whether any terrain adjustment was applied.

AOI provenance stores the exact user bbox or center-radius input, normalized WGS84 bounds/geometry, antimeridian status, selected local metric CRS, source pixel window, full/selected grid shape, pixel bounds, and full/partial coverage status. Orientation provenance and 3MF metadata store `east_axis`, `north_axis`, `north_edge`, `source_bounds`, and `orientation_transform`.

Network builds add `source_acquisition.json` as a checksummed bundle role. It records canonical request keys, authoritative catalog and tile URLs, dataset id, product-wide fallback decisions, ETag, Last-Modified, response bytes/status, content SHA-256, cache hit/miss/corrupt state, bounded network attempts, user and normalized AOI, source-footprint crop, licence URL, attribution, liability notice, and the SHA-256 of the acquired metric raster. The same object is embedded in `provenance.json`; the resolved config records the provider and acquisition-manifest path.


Copernicus AWS acquisitions also record an exact per-tile S3 object listing and an inventory for EDM (editing), FLM (ancillary filling), HEM (height-error standard deviation), and WBM (modified water) rasters. Every exposed source object retains URL, ETag, Last-Modified, byte count, content SHA-256, and cache status. A quality raster is published only when every selected DEM tile exposes the role and its source CRS, transform, width, and height align exactly with the corresponding DEM. Values are not remapped: the aligned AOI raster uses nearest-neighbour reprojection and the identical DEM coverage-crop window. Complete masks are copied into build bundles as `source_quality_edm`, `source_quality_flm`, `source_quality_hem`, and `source_quality_wbm` manifest roles; absent or incomplete roles remain explicit inventory decisions.


Provider-selection provenance stores the complete policy, candidate evaluations, deterministic rank tuples/order, fetch attempts, exact error types/messages, retained-evidence decisions, selected provider/dataset, and selection reasons. The exact same object is present in `source_acquisition.json` and `provenance.json`; build orchestration does not replace it with a simplified success record.

Resolved-place acquisitions additionally store the normalized query, candidate status/list, explicit candidate id/display name, WGS84 candidate bbox, canonical request URL, response SHA-256/bytes/ETag/Last-Modified, cache state, bounded attempts, OpenStreetMap attribution, and usage-policy decisions. Ambiguous searches are emitted as candidates and do not create a raster until one id is explicitly selected.

## Tile-set provenance and assembly identity

A Phase 5 tile set starts from an existing verified build and never substitutes or reacquires terrain. `tile-layout.json` records the processed grid shape, model/tile physical sizes, overlap cells, row/column origins, +X/+Y axes, stable layout digest, per-tile core/sampling windows, physical bounds, and neighbors.

Every tile publishes `tile_provenance.json`, `tile_validation.json`, and `tile_manifest.json`. Provenance binds the source build-manifest SHA-256, retained raw source DEM SHA-256, processed DEM SHA-256, dataset/orientation/source-bounds objects, CRS, window transform, core cell/sample windows, overlap sampling window, physical bounds, and north/west identity. Validation records sample/core grid shapes, finite elevations, binary original NoData mask, NoData count/fraction, sample/core extrema, transform, and required-check status. The tile manifest binds each GeoTIFF/JSON role and embeds the exact validation object.

Root `coverage_map.json` records north-to-south rows of west-to-east tile IDs. `seam_report.json` records the stable east/south adjacency list, shared-core and overlap windows/sample counts, elevation tolerance and max/mean/mismatch measurements, original NoData-mask mismatches, CRS equality, transform alignment error in metres, aggregate status, source manifest identity, and layout identity. `assembly_manifest.json` binds the canonical layout, coverage-map, and seam-report hashes plus source identities, overlap/grid shape, and every relative tile path, manifest hash, artifact hash, core window, sampling window, and physical bounds.

Strict verification rejects unsafe relative paths, non-canonical JSON, missing/tampered roles, mismatched identities, raster/report differences, and extracted values that differ from the declared source sampling window. When a seam report is present, verification checks its SHA-256 and fully remeasures it from the tile rasters using the recorded tolerance. Legacy assembly manifests may omit both seam fields and reopen as `not-reported`; new extraction always emits the report. A repeated extraction is compared by relative path and SHA-256 before any determinism claim is published.

## Tile mesh provenance and assembly identity

A mesh set is a separate immutable derivative of a verified raster tile set. `tile-mesh-assembly-manifest.json` binds the canonical layout, source tile assembly/seam hashes, source build manifest and STL hashes, exact source `ScalingResult`, global axes/origin, coverage PNG, assembly validation, and every relative per-tile mesh role. Each `tile_mesh_manifest.json` binds its source tile manifest and processed DEM hash plus global physical bounds, STL/3MF/GLB/validation paths and SHA-256 values.

`tile_mesh_validation.json` records the core sample shape, expected and reopened global bounds, expected and reopened peak coordinates, triangle counts, strict 3MF warning count, orientation metadata, and the complete reopened STL geometry report. The root assembly validation records every mesh adjacency's sample counts, planar alignment and Z gap; source versus assembled bounds; source volume versus summed tile volume and tolerance; expected/summed/overlapping footprint area; coverage image dimensions; and the aggregate pass decision. Global-frame artifacts are not described as print-local or sliced until those later transformations and slicer results exist.
